# PR-G：性能基线与服务端优化

**当前结果只证明本地服务端改动的效果，不证明 PRD 14.1 六项上线指标已全部达标。** 未调用真实模型、未访问测试服务器或 RDS，也未测 iPhone 输入反馈、移动网络、HTTP/JSON 传输及页面渲染。发布候选环境的 Node 24、最低支持机型、网络参数和并发规模还需固定并验收。

## 六项验收目标与当前覆盖

| PRD 14.1 项目 | 原门槛 | 本工具覆盖 | 上线验收状态 |
| --- | --- | --- | --- |
| 发送和点击本地反馈 | 200 ms 内，**不是 P95 指标** | 无 iOS UI 计时 | 待最低机型实测 |
| 单条明确记录 | 发送→成功回执 P95 ≤ 5 s | `Chat.send`，即时 FakeLlm，含实际 PostgreSQL 写入及回执计算 | 仅服务端子路径；模型和网络待测 |
| 明确计划创建 | 发送→可用计划卡片 P95 ≤ 10 s | 从 99 个计划创建到 100 个，实际落库 | 仅服务端子路径；模型、网络和卡片显示待测 |
| 常规数据查询 | 发送→完整结果 P95 ≤ 5 s | `Chat.send` 查询本月账本，实际 SQL 汇总 | 仅服务端子路径；真实模型和完整查询分布待测 |
| 已有计划详情 | 已登录/正常网络 P95 ≤ 2 s | 分别测账本与学习详情服务函数 | HTTP、鉴权和渲染待测 |
| 写入后当前页面刷新 | 回执后 P95 ≤ 1 s；1 s/5 s 反馈状态 | 100 计划列表刷新服务函数；详情另测 | 不能替代 F 的客户端刷新与超时状态验收 |

不将即时模拟模型的结果减去或换算成真实模型 P95，不把人工查询延迟称为真实 RDS 网络。此脚本不发外部请求、不消耗模型预算，不读取 `.env`。

## 复现方式与数据

安装依赖后在 `server` 目录运行：

```sh
PERF_DATABASE_URL=postgresql://planplan@127.0.0.1:55438/postgres PERF_LABEL=local pnpm perf
PERF_DATABASE_URL=postgresql://planplan@127.0.0.1:55438/postgres PERF_LABEL=delay5 PERF_QUERY_DELAY_MS=5 PERF_SAMPLES=20 pnpm perf
PERF_DATABASE_URL=postgresql://planplan@127.0.0.1:55438/postgres PERF_LABEL=concurrency4 PERF_READ_CONCURRENCY=4 PERF_SAMPLES=100 pnpm perf
```

这是本地临时 PostgreSQL 示例，不是线上连接。连接必须为 localhost/loopback，禁止 URL 查询参数覆盖连接选项。脚本生成随机 `perf_*` schema，先确认 `current_schema()`，再迁移和写入；最后只删除该 schema，绝不清空 public 或其他测试 schema。异常也会关闭连接并清理；被强制终止时由操作者按报告时点核对遗留的 `perf_*`，不能批量删除未知 schema。

- 确定性合成数据 `synthetic-v1`：100 个计划（1 账本、99 学习），10,000 条记录（6,500 支出、500 退款、3,000 学习）。账本覆盖一年、含跨月退款，学习覆盖近一个月；第 100 个计划为空，供创建测试使用。无真实用户数据。
- `PERF_TODAY=YYYY-MM-DD` 可固定业务日期，默认当天上海日期。ID 和金额由固定规则生成；记录时点、数据库缓存和宿主调度仍会产生测量差异。
- 每条场景先预热 3 次，再取默认 50 个样本；P95 用 nearest-rank `ceil(0.95 × N)`。至少 20、最多 1,000 个样本。这里的 20 样本延迟实验只能揭示量级，不能给出稳定的生产置信区间。
- 默认读/写并发均为 1；可把读并发设到 1–20，本次另测 4。写入固定串行并在计时外清理，使记录数量回到 10,000；创建每次从 99 到 100 个计划后清理。不是 20 个真实账户的混合流量压测。
- 记录耗时、应用 SQL 次数、数据库返回行数；事务内部 BEGIN/锁/COMMIT 不计入 SQL 次数。人工延迟加在每次应用 SQL 前，不代表全部数据库往返，更不代表客户端网络。
- 每次写出 JSON 环境、fixture、采样方法、代码 commit 和结果。优化后附实际汇总 SQL 的 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`。不要覆盖留档文件比较不同环境。

## 本次测量

2026-10-27，本地 Apple M4 Pro / arm64 / 14 核、Node **23.11.0**、PostgreSQL 17.9 Homebrew、热缓存。生产镜像为 Node 24，这组测量需在发布候选环境重跑。前后业务日期相同，前后均是同一合成数据规则。基线工具可在 `dc63fc8` 复现，优化代码 `a2bc1a6`；JSON 中保留各次实际源码 HEAD。

| 账本详情 | 24.29 | 4.88 | 4 → 6 | 7,003 → 225 |
| 学习详情 | 0.89 | 1.11 | 6 → 7 | 35 → 21 |
| 100 计划列表刷新 | 59.10 | 4.09 | 301 → 6 | 10,300 → 685 |

来源：[优化前](reports/before-local.json)、[优化后](reports/after-local.json)。学习详情在本夹具中每计划约 31 条记录，增加一次有界查询后略慢；不隐去这个回归。拆开周期目录、按日汇总和本周明细，是为了不再读整段历史。账本详情也从 4 次变成 6 次查询，减少历史明细传输的收益在本夹具上更明显。

人为每次查询增加 5 ms 后，计划列表 P95 从 **2007.30 ms → 39.94 ms**；查询 **763.89 → 112.96 ms**；记录 **832.00 → 222.02 ms**；创建 **816.34 → 166.72 ms**。学习详情 **39.42 → 42.79 ms**，仍保留在报告中。来源：[延迟实验前](reports/before-delay5.json)、[延迟实验后](reports/after-delay5.json)。这说明减少 N+1 往返的价值，不能据此宣称实网达标。

4 个并发读、每场景 100 样本时，账本详情/学习详情/列表刷新 P95 分别为 **6.05 / 1.21 / 7.75 ms**；写入仍串行。来源：[并发读结果](reports/after-concurrency4.json)。

## 实现与正确性

- 对话准备 100 个计划目标时，规则查询从每计划一次改为一次批量查询；提示词的目标、计划顺序和展示字段保持同样的业务含义。
- 计划列表批量加载规则、生命周期、当前周每日合计，最多 6 次应用 SQL；查询 overview 复用相同批量路径。
- 账本在 SQL 中按日期/类别汇总整数金额和计数，退款仍按退款发生日归属、类别来自原支出；只分页取当前月明细，单笔支出的累计退款仍涵盖所有月份。
- 学习统计按日汇总分钟和 session 数，只取所选周/前一周，保留首周目标、归档周、不完整目标和同日多条记录语义。
- 原纯业务计算函数仍作为独立 oracle。新增大夹具核对跨月退款、金额/计数/日趋势、同日 session、软删除、归档恢复周，以及不完整目标。查询次数断言防止重新引入 N+1。完整 PostgreSQL 164 项通过，PGlite 163 项通过、1 个仅真实 PG 的并发池测试跳过。

实际查询计划使用现有 `records_plan_date` 位图索引定位本月数据；退款原记录在数据库内部作一次 hash join，未把全部原始记录传回应用。该夹具下汇总 SQL 执行约 1.31 ms。没有证据要求新索引，因此本 PR **不新增迁移 008**，不改已发布迁移，也不跨过 H/J 迁移顺序。更大历史/更多账户需要重新测量，不能从 10,000 条推断任意规模。

## 候选发布环境还要完成

固定最低支持 iPhone、iOS、构建号、Node24 镜像 digest、RDS 规格/区域、同地域 DB 往返、Wi-Fi/蜂窝网络与并发账户数。真实模型和备用模型分别记录超时/失败，失败计入成功率并单独报告，不能丢弃慢样本。客户端从发送/点击开始，用实际成功回执、卡片可交互、完整查询结果或 `dataVersion` 刷新完成作为终点；登录、网络和渲染都计入。每场景建议至少 100 个有效测量并保留失败分母，比较冷/热路径。真实付费评测和真机采样本 PR 没有执行。
