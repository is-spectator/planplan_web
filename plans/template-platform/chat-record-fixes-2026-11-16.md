| 问题 | 证据与判断 | 修复后行为 |
| --- | --- | --- |
| F050 / F060 买书被记为“购物” | 旧真实回执的金额、咖啡分类和阅读分钟正确，但书籍分类与冻结预期不符。原提示词仅要求按内容推断，没有说明书籍、教材和课程的用途分类。 | 提示词明确这些支出默认归“学习”，用户明确指定分类时优先尊重用户；不以“买”字一律归购物。实际模型效果交由新指纹评测验证。 |
| F052 耳机退款未找到原消费 | 场景中确有 10/18 的耳机 199 元支出。旧真实输出没有保留原始 turn，不能断言当时模型的具体 note。源码确认查询直接把 note 整串作为 ILIKE 条件，本地可复现“耳机退款199元到账了”无法匹配原备注“耳机”。 | 提示模型从已有支出选 ID、备注仅写原消费内容；后端仅移除退款状态后缀，按字面值检索。唯一内容匹配才关联；无匹配、多个匹配或非法引用则让用户选原支出，即使退回列表只有一条也不擅自关联。 |
| 未到账或外币退款可能被当作人民币事实 | 原退款分支没有检查 `is_fact` 和外币标记；其他写入分支已有相应保护。 | 未到账/未来退款不新增，外币要求明确人民币金额；原退款总额上限、日期及所有权校验保留。 |
| 归档通用计划对话丢失目标 | `pickGeneric` 原先只查 active/pre.restore，归档 scope 被忽略；有另一个进行中的通用计划时可能转写，只有归档计划时错误要求去市场采用模板。 | 显式 ID 和当前归档 scope 保留为目标，写入前出现“恢复并记录”，确认后恢复与记录整批保存。取消不恢复；查询历史保持只读。明确不存在、无权限或类型不符的目标不自动转写其他计划。 |
| 归档阅读计划也可能转写到其他阅读计划 | 进一步审阅发现 `pickStudy` 同样仅接受 active scope，而且无效显式 ID 可继续按 activity 或唯一活跃计划回退。 | 阅读计划采用相同的归属规则；明确 ID 无效即追问，不继续回退。归档范围先确认恢复，用户明确改记到其他计划时仍尊重该选择。 |

## 后续发现与 R12：已打开级联删除确认后的退款变动

以下保留 R11 冻结时的发现与方案比较。随后已单独授权 R12 实现关联集合快照，当前契约与验证结果见[关联退款删除确认 v1](refund-confirmation-v1.md)；上面的 643 项结果仍只属于 R12 之前的候选。

这是独立审阅发现的既有边界，不是本次详情刷新按钮修复引入。发现时的 `DeleteRecord` 以打开时的 `original` 快照显示“同时删除关联退款（共 ¥金额）”，**没有列出退款笔数、明细或关联集合标识**。打开后另一端新增、修改、删除或撤销退款，不会同步增加原支出的 `version`；旧实现提交 `includeRefunds:true` 时，引擎会重新取得并删除当时所有有效退款。因此“原来有一笔退款并已勾选 → 别处新增另一笔 → 确认删除”的场景，可能连同尚未展示的新退款一并移出统计。原来没有退款且 `includeRefunds:false` 的场景仍会被服务端 `has_refunds` 拒绝，不会静默扩大删除。

当前删除是软删除，并把原支出与本次所有实际删除的退款写入同一操作回执和撤销步骤。只要这些记录未再发生冲突且操作仍可撤销，**撤销整次操作**可以恢复整组；已有 `engine.test.ts` 覆盖级联删除后整次撤销及净额恢复。页面提供该操作的撤销入口。这降低恢复成本，但不等于用户事先确认了新增退款，不能把“能撤销”当作并发确认正确。

两个修复选项的成本与边界：

| 方案 | 影响 | 判断 |
| --- | --- | --- |
| 所有退款增/改/删/撤销同时增加原支出 `version` | 无需新 SQL 列，但必须覆盖退款四类变动、级联删除和逐条/整次撤销、批量操作及回执版本。当前 UndoStep 按精确版本检查，若在恢复退款步骤中先增加父支出版本，会使随后恢复父支出的步骤自冲突；必须设计一次事务内去重更新和撤销快照策略。既有原支出编辑/撤销可能变得更保守。旧调用若不带 `expectedVersion`（包括当前普通记录的对话删除）仍不会获得保护。 | 影响面较大，不适合在已冻结候选里只加几条 UPDATE。 |
| 删除动作携带预期关联退款集合 | 增加只读详情中的集合摘要，以及 `delete_record.expectedRefundSnapshot`；不改变通用记录版本和既有 UndoStep。服务器从原支出 ID/版本和按 ID 排序的有效退款 ID/版本生成摘要，并让展示金额/笔数来自同一次一致读取。删除事务内、现有用户锁下重新核对摘要，不同即 409 且零写入。 | 推荐独立小功能切片，影响较窄，通常无需数据库迁移。不能只比金额或笔数，否则等额替换仍漏检。 |

- [ ] 定义 `RecordResponse.refundSnapshot = { token, count, totalCents }` 与 `delete_record.expectedRefundSnapshot`；同一详情读取生成展示值和摘要，避免两次查询混用不同状态。界面固定展示待确认集合的笔数/总额，后台刷新不得悄悄扩大已确认集合。
- [ ] 在删除事务中核对原版本和关联摘要，再整批软删除；不一致返回冲突及最新确认资料。既有成功请求按原 `clientOpId` 返回原回执，不因当前集合已删除而破坏恢复/幂等。
- [ ] 同步网页删除表单和服务端生成的对话删除确认。明确旧客户端政策：可保持非级联删除；无摘要的 `includeRefunds:true` 要求重新确认/升级，不能一边保留绕过路径一边宣称所有客户端均已保护。
- [ ] 验证确认后新增、改金额、改日期/备注、删除、撤销退款，以及“总额与笔数相同但 ID 不同”均拒绝旧确认；新快照明确确认后成功。覆盖断网后原 ID 恢复、409 后重新核对、两个并发请求串行化、完整撤销及旧客户端分支。
