# R12 退款删除确认网页验收

验收目标：删除支出时，页面只提交用户打开确认时核对的关联退款集合。另一个页面新增、移除或修改退款后，旧确认必须停止，用户重新核对后才能重新提交。用语保持「计划」，页面只显示退款笔数、金额和下一步操作，不显示内部快照或调试字段。

生产源码冻结为 `86c64c6c290a6d3293ed43f13cd735665802a1f5f8a287308bc69f61e6198413`；Linux 构建为 `816b4b14226a8e8d457c5cc484948696002ac4dcd83341d96f3200241ab640cc`。本报告与 R11 的 `c0eaa65e…`、148 项历史证据分开保存，不把旧结果算作新源码验证。后端契约见 [refund-confirmation-v1.md](refund-confirmation-v1.md)。本报告不代表生产发布完成。

页面实现位于 `RecordInspector.tsx`、`RecoveryCenter.tsx`、`contracts.ts`，配合 `RecoveryProvider.tsx` 的冲突协议。确认固定记录版本及退款快照；零退款也提交快照；缺少快照时停止提交；409 后当前确认在本地保持失效，即使全局冲突提示被清除也不会自动恢复；「取消并重新核对」读取最新内容后，还需再次打开确认并勾选关联退款。未知响应仍沿用恢复队列的原请求 ID 与原快照。

新增受控浏览器用例 6 项，覆盖新增退款、移除退款且原支出版本不变、同额内容编辑、缺少快照、旧确认错误的中文对照、未知响应后原请求重试。旧详情刷新用例 2 项保留「版本不变」与「另有修改」两种情况。新增真实双页面用例 3 项，分别核对新增、移除及同额编辑：旧请求返回 409；原支出版本不变；失败前后的记录详情和账户数据版本完全相同；重新确认后才删除当前集合。

所有实际流程只使用既有正常 UI 登录的合成账户，未伪造会话，未读取用户浏览器配置。浏览器拦截禁止真实聊天或创作模型 POST，8788 同时使用 stub 模式。现有来源消息用例只读读取此前保存的模型结果，没有新增模型请求。Chromium 与 WebKit 来自已有缓存；WebKit 自动化不是实体 iPhone、真机键盘或真人试用验收。
