## 如何分给多人

**新增 5 支没有前置实施 PR，可以立即分别领取。** PR-001 已合并、PR-002 已有人实施；不要重新开发它们。并行按功能文件划分，不按“前端统一交一人、后端统一交一人”划分。建议每位实施者使用独立分支和 worktree／checkout，不在同一个工作目录同时改代码。

如果有 4 位实施者，可以这样安排；同一行内按顺序做，不同的行同时开始：

| 实施者 | 第一支 | 下一支 | 为什么这样分 |
| --- | --- | --- | --- |
| A | PR-007 自动化检查 | 协调新专项接入及合并检查 | 尽早提供检查；PR-002 继续由原实施者负责 |
| B | PR-006 导出 | 复核导出兼容与 PG 并发证据 | 集中处理完整性、快照与文本安全，不重复 PR-001 |
| C | PR-003 市场导航 | PR-004 审核分页 | 两项独立列表页面，按各自 API 与 UI 语义实现 |

人数更多时，PR-004 也可立即分给第五人；上表只是人员安排，不是技术依赖。只有一个新增实施者时，建议顺序为 007 → 005 → 006 → 003 → 004，现有 PR-002 保持原负责人。

## 合并与组合验收

1. PR-007 优先合并有利于后续验证，但其他新 PR 可以先完成与评审。PR-003／004／005／006 没有相互合并顺序；PR-001 已在 main，PR-002 由现有评审继续。合并相邻能力后必须做下列组合检查。
2. PR-001＋002：聊天／创作的准确失败提示能进入手动流程；丢响应、处理中及重试关页仍只能核对原请求。不能因为文案变化使按钮失效。
3. PR-002＋005：失败后直接打开空白／已有草稿；非法统计可定位且不能保存，修正后仅保存一次，手机面板与版本冲突保持。
4. PR-003＋004：合成审核者改变模板可用状态后，市场旧页可恢复；待审／下架版本仍不能通过详情直接采用。两支无需互相调用新增 helper。
5. PR-006：验证新增 `records.json` 与旧 ZIP 文件／下载入口兼容。其余功能新增的数据仍按本账号、同一快照导出；不要只数 ZIP 文件。
6. PR-007 建立用例发现与分类机制；之后各功能 PR 的新专项接入由合并协调者核对，必要时更新 CI 分类，确保所有新专项在最终合并 commit 上运行。只有某分支自己的旧检查通过，不足以证明组合可用；不把失败转成 skip，也不重复使用旧测试数。

组合检查由合并协调者组织，必要时提交只含组合回归的补充 PR；当前没有虚构第八项“已完成”任务。合并后部署仍单独记录来源 commit、源码包与实际验收；自动化检查不会自动部署。
