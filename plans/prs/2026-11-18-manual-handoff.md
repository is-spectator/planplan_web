## 已确认的问题

当前恢复提示中的“暂不重试，继续手动记录／手动编辑”只调用 `RecoveryProvider.cancelConfirmation()`：清除本浏览器的待重试条目，再显示一句提示。用户仍需自行找到计划、打开表单，或再次打开草稿编辑器。

现有代码已具备所需基础：

- `src/lib/RecoveryProvider.tsx` 保存并显示 `transient`、`unknown`、`confirmation` 等恢复状态，支持同 ID 重试与核对结果。
- `src/lib/useChatRequest.tsx` 的原请求包含 `scopePlanId`、`text`、`inputAt`；创作消息请求包含 `draftId`。不必让模型再猜目标。
- `src/features/plans/PlanDetail.tsx`、`src/features/templates/GenericPlanDetail.tsx` 已有记录表单，但通过页面本地 `adding` 状态打开，目前没有专用的导航打开入口。
- `src/features/creation/CreationWorkspace.tsx` 已有 `DefinitionEditor`，支持现有定义与空白草稿；手机默认显示对话标签，取消重试不会自动进入编辑面板。

这些是基于单仓 `main` 提交 `375a53b5a3f2e275bdadb223a47302c8e7de0aca` 的源码核对，不是本 PR 的通过证据。实施前重新核对最新主分支。

## 用户流程

| 入口 | 用户动作与结果 |
| --- | --- |
| 有计划范围的聊天明确失败 | 提供含义明确的“取消重试，手动添加记录”。取消当前失败请求的重试后，进入该 `scopePlanId` 的计划并打开现有新增记录表单。 |
| 没有计划范围的聊天明确失败 | 提供“取消重试，选择计划记录”。进入进行中计划的选择界面；用户明确选定计划后才打开表单，不默认选第一项或最近使用项。 |
| 创作消息明确失败 | 提供“取消重试，手动编辑”。进入该 `draftId`，读取最新草稿并打开现有编辑器；手机切到可见的编辑面板。定义尚为空时进入空白编辑。 |
| 其他页面的全局恢复入口 | 使用同一套行为，目标仍来自实际取消的原请求，不能使用当前页面或最近访问的计划。 |

聊天也能查询、修改、删除和退款，不能把任意失败消息当成“新增记录”意图。本 PR 的聊天按钮必须明确表示**用户主动改用新增记录表单**；不根据失败文字推断操作，不自动打开删除、退款或设置流程。用户也可以继续使用原有核对／重试路径。

没有进行中计划时，显示空状态和现有“去市场／新建计划”入口；不自动创建或采用模板。原目标归档、删除、无权限或暂时无法读取时，说明实际状态并提供返回／重读入口；不能悄悄改用别的计划、恢复归档或新建草稿。

## 实施要求

### 1. 安全结束本次重试，再进入手动界面

新动作的适用条件为 `status === 'transient' && (kind === 'chat' || (kind === 'creation' && body.action === 'message'))`，即聊天和创作消息都必须已明确失败。普通操作的重复确认仍使用原“取消本次提交”；其他创作操作的取消保持现有语义。

新增或拆分一个窄范围的方法，接收用户点击时的预期请求 ID。在现有 `withSessionLock` 内重新读取持久化条目，核对当前账号、请求 ID、kind/action 和状态；只有仍符合条件时才能删除该条目并返回**实际取消的请求**。调用方只有拿到成功结果、确认账号仍一致后才导航，不能使用点击前缓存的旧条目。

正在重试、处理中、结果未知或核对失败时不能转手动。锁等待期间另一标签页已完成／替换请求、用户切换账号、条目已清除时，应同步最新状态，不清除新任务、不跳转。核对出现 `processing` 后，不能因为旧 UI 或旧持久化状态仍是 `transient` 就允许取消。保留既有同 ID 重试、跨标签锁与广播规则，不增加自动重发。

当前 `post()` 在重试出站前不会把旧 `transient` 改为持久化的 `unknown`，因此仅检查锁与内存 `busy` 不够：发出请求后关闭标签，另一页可能仍读到旧失败状态。本 PR 应在重试 POST 发出前先成功持久化 `unknown`，读取 `processing` 或核对失败时也同步为不可转手动的待核对状态，待服务器再次明确返回失败后才恢复 `transient`。沿用现有状态与原请求 ID／请求体，不新增后端协议；持久化失败不能继续发出重试。此修补是安全开放新入口的必要部分。

`RecoveryProvider` 经 `AccountScope` 位于 `RouterProvider` 外，不能直接往 Provider 中添加 `useNavigate`。在路由内的恢复控件或专用桥接组件执行导航，Provider 只负责恢复条目的安全变更。

### 2. 复用表单并处理导航

当前路由为 `/plans`、`/plans/:planId`、`/create/:draftId`。为现有页面增加受控的打开意图，可以使用轻量组件／hook；不要重写 `RecordForm`、`GenericRecordForm` 或 `DefinitionEditor`。

打开前读取当前账号可见的计划／草稿，确认目标仍可用。创作以最新读取的定义与版本进入编辑，保留既有版本冲突处理；不能拿失败请求中的旧 `expectedVersion` 覆盖最新草稿。计划和模板的默认值、日期／跨日复核、幂等保存、退款与版本保护继续走已有表单链路。

相同页面内切换也要生效；清楚规定打开意图何时消费，关闭后不能被重渲染或浏览器返回反复打开。若用户已有未保存的表单／编辑内容，不静默覆盖。打开后焦点落在表单标题或合适输入项，320px／390px 窄屏无需返回对话标签寻找编辑器。

无范围的计划选择复用现有计划列表数据与样式，只展示本账号进行中计划。计划名、模板名称用于识别，不显示请求 ID、内部类型、模型名或其他调试信息。

### 3. 保留原文供参考，不代替用户填写

从实际取消的请求带出原文字，在目标表单／编辑器旁提供可展开的“原消息”参考。复用创作已有的原输入恢复逻辑；不要覆盖用户后来修改的输入，也不要把已有对话输入的删除当成“取消重试”。

原文作为普通文本显示，不自动解析、执行或预填金额、日期、分钟、单位、书名等业务字段。手动保存属于用户确认后的新操作，使用现有表单产生的独立操作 ID，不能复用已经取消的聊天／创作消息 ID。

原文和打开意图只需在本次手动流程内保留，使用账号绑定的内存状态即可；不要放入 URL、日志或新增长期存储。关闭／完成手动流程、退出或切换账号后清除。刷新后可回到正常页面，不自动重发或提交；本 PR 不新增跨刷新手动草稿存储。

## 验收矩阵

| 场景 | 必须核对的结果 |
| --- | --- |
| 计划内聊天失败，在聊天页或另一页面点击转手动 | 使用原 `scopePlanId`；正确表单可见；原文仅供参考；本次动作没有模型调用或业务 POST |
| 全局聊天失败 | 必须由用户选定计划；空列表、读取失败可理解；不会自动选计划或创建任何内容 |
| 记账、阅读、饮水／通用计划 | 分别进入既有表单；默认值和校验不变，原文不会被猜成结构化字段 |

| 空白／已有定义的创作失败 | 进入原草稿最新定义的编辑器；手机编辑面板可见，原文可查；没有保存或采用模板 |
| 草稿已被修改、目标已归档／删除或无权访问 | 不用旧快照覆盖、不改目标、不自动恢复／新建；提供恰当状态和返回入口 |

| 重复确认、连续双击、两标签并发、账号切换 | 既有重复确认语义保留；只处理指定失败条目；不误取消新任务，不泄漏原文，不跨账号跳转 |
