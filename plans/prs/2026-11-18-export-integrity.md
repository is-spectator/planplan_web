## 已核对的缺口

以下为单仓 `main` 提交 `7c03257` 的源码事实，尚不是修复后的验证结论：

1. `server/src/services/community.ts` 的 `exportCommunityData()` 调用 `listAuthorCommunity(q, userId, { limit: 100, offset: 0 })`，随后只返回这一页的 `works`。作者列表是分页接口；社区作品没有对应的终身 100 件上限。私人草稿的同时保留上限不能当作历史社区作品总量上限，因此导出存在截断路径。
2. `server/src/api/app.ts` 的导出路由直接调用 `buildExport(db, uid(c))`。`server/src/services/export.ts` 分别读取计划、记录、目标区间、模板、创作、社区及反馈，当前没有包在同一个读取快照中；并发保存时可能把前后两个版本拼进同一 ZIP。
3. `server/src/db/db.ts` 的 PostgreSQL `tx()` 只执行普通 `BEGIN`，不能据此声称多次查询天然属于同一快照。已有 `historyRead()` 使用明确的 `REPEATABLE READ READ ONLY`，可参考其方式；不要把导出错误复用成“历史分页变化”的提示。
4. `export.ts` 的 `csvCell()` 只对逗号、双引号和 LF 加引号，不包含单独 CR，也没有区分用户文本与数值。计划名、备注直接进入 CSV；公式样式的文本前缀未作处理。现有常规导出测试主要检查文件名、包含记录和排除已删除记录，未覆盖这些边界。

目标是修复这三类导出问题，不扩展为备份恢复、账户专项或数据分析产品。

## 实施范围

### 1. 完整导出自己的社区作品

导出 helper 使用导出专用的完整读取方式，或在同一快照内采用稳定游标分批读取。不能只把 `limit` 从 100 改为另一个固定值，也不能绕过页面接口的参数校验后继续依赖有限 offset。

保持原有 `community.json` 结构与权限范围：自己的作品、申请、举报、自己计划的采用来源。`works` 包含自己有权导出的全部状态作品，不因下架或暂停而漏掉自己的历史；其他账号的作品明细、采用者私人记录或反馈不能混入。

普通市场、作者列表、审核队列的分页及状态过滤不变。修改限定在 `exportCommunityData` 及其必要的导出专用 helper，不借此改造全部社区查询。

### 2. 所有文件使用同一读取快照

在导出的公共服务入口建立只读、可重复读事务，所有读取 helper 使用同一个事务 `q`，不能内部重新使用连接池对象。可拆成外层事务入口和内层数据收集器；所有生产调用者都应经过该入口。

事务隔离级别须在业务读取前设置。PostgreSQL 要有两个真实连接交错读写的测试；PGlite 的单连接排队只能证明功能兼容，不能冒充跨连接快照验证。不要为导出持有用户写锁来阻止正常记录，也不要对整个数据库加锁。

本次导出的时间只捕获一次，`exported_at`、上海业务日期及依赖日期的模板配置使用这同一个时点，避免在午夜混用两个日期。数据在事务中读取完毕后，可在事务外生成 CSV／JSON 和压缩 ZIP，缩短持有快照的时间。

这里保证的是 ZIP 内容的一致时点。当前 API 响应文件名另取 `today()`，网页下载名使用会话的 `user.today`；服务端响应文件名可随同一捕获时间调整，但本 PR 不修改前端下载命名，不能声称浏览器文件名也已消除午夜日期差异。文件名不作为数据快照时间的依据。

快照含义是“某一时点的完整一致状态”，不是要求包含下载完成前的每次新保存。事务中途查询失败应使整个导出失败，不能返回缺几个文件却显示成功的 ZIP。审计事件继续沿用原机制，放在只读快照之外，不把事件写入塞入只读事务。

### 3. CSV 可读且保留无损原文

CSV 序列化应正确处理逗号、双引号、LF、CRLF 和单独 CR。维持 UTF-8 BOM、既有列名和金额／分钟口径；不改变用户数据库中的文本。

明确区分“用户文本列”和“数值列”：例如备注、计划名按文本处理，金额／分钟按已有规范数值处理。对用户文本中的公式起始字符 `=`、`+`、`-`、`@`，以及可能影响表格解析的前导空白／制表符／换行组合，采用统一的安全文本前缀策略并写入导出 README。不能仅依赖 CSV 双引号来处理公式，也不能把合法数值列全部改成文本或删掉负号。

仅做安全显示处理会改变 CSV 的字面值，因此本 PR 增加一个明确的无损读取入口：`records.json`，建议结构为 `{ schemaVersion: 1, records: [...] }`，包含本次快照中的有效记录，沿用已有记录投影／稳定 ID 与规范单位。原始备注在该 JSON 中逐字符保留；原始计划名称继续在 `plans.json` 中保留。现有 `generic-records.json` 仍保留，不能为了消除重复就删除老文件或改变其结构。

F01 应先固定新增 JSON 的字段和单位约定。`recordView()` 的 `refundedCents` 默认可能是 `null`，表示未提供该派生汇总，不能改写成零退款；可明确省略／标记未计算，或在同一快照内计算并验证。原始退款关联和金额仍需保留，不能用一个未计算的汇总字段代替事实。

这会使当前 ZIP 从 11 个文件增加为 12 个，属于有意的兼容性增补。更新导出 `README.txt`：区分面向表格阅读的 CSV 与保留原文的 JSON，说明新增文件、字段口径及安全前缀；旧文件名、列名和字段继续可用。不要把 SQL 内部行、用户凭据、恢复令牌或其他账号数据原样放进 JSON。

安全前缀策略需要明确的输入／输出样例与回归。可补充常用表格软件导入检查，但未实际运行某个软件时不得写“所有表格软件均已验证”。
