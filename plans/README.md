# PlanPlan Web MVP 规划

规划日期：2026-11-16（Asia/Shanghai）

状态：待实施。本文档描述计划，不表示功能、部署或验收已经完成。

## 目标与交付边界

让受邀用户通过一个真实 HTTPS 地址，自行完成注册、记录、查询、纠错，并在以后登录时继续使用。电脑和手机浏览器共用现有 PlanPlan 账户与业务数据。

MVP 面向最多 20 个受邀邮箱，先小范围体验，再逐版扩大。这个上限来自现有后端邮箱白名单配置；人数为每阶段累计规模，不是新增人数。开放公众注册不在本轮范围。

Web 代码放在本仓库 `is-spectator/planplan_web`；业务后端继续位于 `is-spectator/planplan`。此次提交仅建立规划，不包含应用实现、资源配置或上线。

## 版本路线

| 版本 | 用户得到什么 | 建议累计体验人数 | 版本完成条件 | 说明 |
| --- | --- | --- | --- | --- |
| [v0.1 首次可用](v0.1-first-use.md) | 从邀请注册到对话记账、查看、纠错、重新登录的完整闭环 | 3–5 人 | 真实邮箱、模型、数据库和 HTTPS 可用；首版可靠性与账户底线通过 | 首次可供外部用户体验 |
| [v0.2 日常管理](v0.2-daily-use.md) | 完整账本、多学习计划、历史周期、退款和计划管理 | 5–10 人 | 两类计划能持续使用，聊天、详情和导出数据一致 | 扩展到日常使用 |
| [v0.3 MVP 验收版](v0.3-mvp-release.md) | 跨端继续使用、待核对事项处理、反馈入口和经过验证的移动体验 | 10–20 人 | 完整回归、真实试用、恢复及回滚验收完成 | 本轮 MVP 完成点 |

版本按验收推进，不把“页面做完”视为可发布。先通过技术、账户和数据恢复等共用门槛，再向本阶段限定人群开放候选版；收集该版要求的真实试用证据后，才标记版本完成并进入下一阶段。人数仅是建议规模。任何版本都不得以假数据页面、开发免密登录或只能在开发者电脑运行的服务代替交付。

## MVP 完成定义

以下均为目标，当前尚未执行验收：

1. 受邀用户无需开发者代操作，即可注册、登录、创建计划、记账或记录学习、查询、纠错和重新登录恢复。
2. 一个人民币账本和多个学习计划可用；金额按分、学习按分钟、业务日期按上海时区处理。
3. 无 AI 授权或模型暂不可用时，已有计划仍可通过手动表单维护；创建计划也提供相应手动入口。
4. 重复点击、超时、刷新、断网恢复和并发编辑不会导致已知的重复记账、错误覆盖或跨账户数据混用。
5. 数据导出、退出所有设备、账户删除有可用入口及准确状态；真实运行环境有可验证的持久化与恢复能力。
6. 通过 v0.3 的浏览器矩阵和真实试用标准；没有未解决的阻断问题。

## 实施顺序与分工

1. 先落实共同约定中的 Web 会话接口和部署资源，完成可部署的最小骨架。
2. 前端与后端可并行：前端按固定响应契约开发；后端在 `planplan` 提交 Web 会话适配及契约测试。
3. 完成 v0.1 整条真实链路与共用门槛，再开放第一批候选体验；试用通过后确认版本完成。v0.2、v0.3 依次继承前版能力与验收底线。
4. 每版登记前端提交、后端提交、迁移状态和已测环境；只发布经过验证的组合。

角色责任：产品维护范围和受邀名单；前端负责浏览器体验；后端负责认证与接口兼容；部署负责人负责真实资源、发布与恢复；验收负责人保存测试及试用证据。小团队可以由同一人承担多个角色，但发布记录必须写明责任人。
